Findings at a glance

Measured on 2026-11-02, with aria2 added on 2026-11-03. rqbit offered the strongest combination of throughput and small application memory in this lab. qBittorrent had the fastest median large-file download. Transmission used little application memory but completed downloads more slowly. rTorrent used very little anonymous memory, with large file mappings and a repeatable upload startup delay. Deluge had the largest application memory footprint and highest CPU cost for the large download. aria2 offered another small application footprint, with moderate bulk-transfer rates and the slowest cached recheck in this suite.

The synthetic findings come from actual BitTorrent transfers: 180 accepted phases, three repetitions per client, 270 GiB of payload. All data and torrent metadata were generated locally. The Compose runtime network was internal, with no public torrents, internet trackers, magnets, or published ports.

01

Ubuntu public download

The main public experiment completed all 36 planned attempts: six fresh attempts for each of six clients. Thirty downloads finished within the 15-minute deadline and passed independent filesystem SHA-256 verification; six timed out. It ran on 2026-11-03 from 19:36:00 to 22:08:00 UTC. This is separate from the synthetic lab. The host used 1000baseT full duplex Ethernet throughout: all 920 sanitized observations confirmed active gigabit media and primary IPv4/IPv6 routes through en9. This establishes the local link, not ISP capacity.

Main findings. rTorrent had the highest completed-download median, 41.09 MiB/s, and completed 6/6. rqbit reached 35.43 MiB/s and qBittorrent 31.71 MiB/s, also 6/6. aria2 completed 5/6 at a conditional median of 32.38 MiB/s, but its 9.65–84.99 MiB/s range and timeout show substantial variability. Transmission completed 5/6 at 14.52 MiB/s; its timeout reached approximately 99.956% reported progress without completing. Deluge's native empty-interface configuration completed only 2/6, at 11.28 MiB/s. Its loaded-download estimate therefore has only two observations; the separately registered interface follow-up below addresses that limitation without replacing these failures.

The source was the unmodified official Ubuntu 26.04.1 live server AMD64 torrent: 2,927,861,760 bytes, 2,792.23 MiB (2.73 GiB), 256 KiB pieces, 11,169 pieces, two HTTPS tracker endpoints, and no web seeds. The torrent provenance records the metadata and official checksum source. Each completed rate divides this fixed payload by elapsed time from API submission through reported completion, including discovery, initialization, transfer, and final-piece delays. Daemon startup and configuration happen before the timer; independent SHA-256 verification happens afterward with the client stopped. MiB/s means binary megabytes per second; multiply by 8.388608 for decimal Mb/s.

Design registered before measurement. A seeded six-round Williams design placed every client once in each execution position and every directed adjacent client pair once within rounds. Cross-round transitions are not included in that balance. The protocol fixes the complete order, six attempts per client, and a 900-second deadline with no early no-progress cutoff. All slots were executed sequentially; no failed or slow attempt was replaced. Configuration, session/DHT state, and destination files were reset for every attempt. This is fresh application state; host/VM filesystem caches were not globally flushed. An already running, warmed-DHT client was not tested. A final piece arriving after the deadline would still count as a timeout here.

The same six pinned versions and native ARM64 Docker environment as the synthetic suite were used, with 2 CPU cores, 1,536 MiB charged memory, and no container swap. Seventeen Python harness files were archived and hash-checked; the measurement code stayed fixed throughout the main experiment. Effective settings were separately recorded and hashed for every attempt. DHT and PEX were enabled, LAN discovery and automatic port forwarding disabled, with native TCP/uTP support where available. Five clients used a 100-peer per-torrent limit; rqbit retained its native peer policy. Aria2 retained its default disabled IPv6 DHT while IPv6 peer transport was enabled. Those native engine differences are part of this deployable-image comparison.

The public Docker network supported outgoing IPv4 and IPv6, with NAT and no forwarded incoming ports; control traffic used a separate internal network. No synthetic peers ran alongside the public experiment. Deluge's empty native listen_interface preference resolves to 0.0.0.0 in Deluge 2.2.0's implementation. An aggregate socket inspection during its second, failed attempt found IPv4 sockets and no IPv6 peer sockets. It changed no settings, but the brief Python helper may add a small amount of CPU/RSS to that failed attempt; the observation record discloses it. Completed-download resource summaries exclude that attempt. No peer addresses or IDs were retained.

Statistics retain failures. Throughput medians, IQRs, and ranges are conditional on verified completion. A failure has no complete-file rate, rather than an invented zero rate. Completion counts show all attempts; a separate deadline-penalized mean assigns every failure the full 900 seconds. Thus the chart's speed ranking and the penalized-time ranking answer different questions. A six-success sample still has a wide Wilson interval; these are descriptive results, with no significance test or universal capacity claim.

Audit: 36 attempts; 30 independent SHA-256 checks; 14,238 resource samples; 920 sanitized Ethernet/route observations. No ISO retained.

This experiment describes cold client state on this host, network, and swarm during the recorded window. It does not estimate universal client capacity. Six trials still have substantial uncertainty; even 6/6 completions gives a Wilson lower bound of about 61%, under a binomial model. Swarm and temporal dependence further limit that model. There are no significance claims.

What the memory figures mean. Among completed downloads, rTorrent's median peak anonymous allocation was only 8.23 MiB, but its median peak RSS was 1,256.35 MiB and working usage 1,513.97 MiB because file mappings/cache are substantial. It cannot be described as an 8 MiB-RAM client. rqbit combined a 19.84 MiB median anonymous peak with 32.53 MiB RSS; aria2's corresponding values were 9.41 and 18.50 MiB across five completions. qBittorrent reached 39.36/73.36 MiB and Transmission 44.56/59.43 MiB. Deluge's two completions reached 122.42/1,498.72 MiB. Anonymous memory excludes file-backed pages; RSS sums resident process mappings and may double-count shared pages. Charged memory includes filesystem cache; working usage subtracts inactive file pages. These counters describe different costs, not minimum RAM requirements.

Every completed transfer approached the configured 1,536 MiB charged limit, mostly through filesystem cache. Small sampled overshoots are allowed temporarily by the Linux cgroup memory controller. No accepted main attempt was OOM-killed. CPU core-seconds are cumulative cgroup CPU usage, not elapsed seconds or CPU percentage; idle timeouts can consume less CPU than a complete transfer. That is why both all-attempt and completed-download resource tables are included.

Observation limits. Resource polling targeted 0.5 seconds, status polling 0.2 seconds, and optional discovery polling 15 seconds. Actual resource gaps differed by client: the largest was 15.242 seconds, and rqbit's was 13.778 seconds. The cadence table makes this visible. Sampled peaks are lower bounds on transient peaks; small memory differences should not be treated as precise rankings. Cumulative CPU and network deltas do not lose work between samples. All peak/median resource values and cumulative deltas were independently recomputed from the 14,238 raw samples. No optional diagnostic RPC errors occurred in the main experiment. Startup/active-window diagnostics are suppressed for rTorrent and rqbit because initialization/hash-scan counters can resemble transferred payload. Their complete-file wall rates, network RX, and filesystem verification remain valid.

Disk handling and integrity. The 30 verified main downloads total 81.80 GiB of ISO payload, demonstrating repeated actual transfers rather than reuse of a preexisting ISO. Each successful attempt's measured network receive count exceeds the full payload. Each attempt deleted the ISO and sidecars and recorded an empty scratch directory: 36/36 cleanups. The clients share one scratch volume, so at most one 2.73 GiB ISO payload is present at a time. The project removes its containers and volumes on exit; no ISO is retained. This is a payload-retention limit, not a cap on Docker's overall image/VM disk allocation. The independent expected SHA-256 from Ubuntu's SHA256SUMS is cc8a95cde20f6ced61a322420de00f10cc3c90ced545daa46cb9c1a117f1d927.

Interpretation. This is a real public-swarm experiment on one connection in one time window, with controlled image versions, resource limits, payload, cold application state, and balanced order. Peer availability, tracker responses, DHT bootstrap, endgame behavior, and ISP conditions remain uncontrolled. The balance mitigates time/order effects; it cannot eliminate them or establish independent, stationary observations. The reported Ubuntu IPv4 tracker problem is relevant context, but does not prove the cause of any individual failure. The earlier rTorrent/aria2 IPv4-only failures do not demonstrate low transfer capacity: both downloaded the complete ISO in this dual-stack main experiment. Nor does aria2's fastest 84.99 MiB/s observation establish a stable maximum. These findings describe the tested cold-start deployment, not an already connected client or every network.

Separate Deluge interface follow-up. The conditional follow-up plan was recorded at 21:10 UTC, before the main experiment finished. Its trigger was fewer than three Deluge completions in the fixed six main attempts; the decision records the actual 2/6. It fixes another six attempts under the same deadline and quotas, changing one client preference: listen_interface binds to the Linux interface carrying the default outgoing route. A paused, untimed preflight verifies IPv4 and IPv6 TCP/UDP sockets before transfers. Binding that interface changes both interface selection and address-family availability; this is not an isolated proof of IPv6 causality. It runs later and remains a separate condition, never pooled into or substituted for the native 36 attempts.

The first interface follow-up exposed an observer defect: optional discovery RPCs timed out and blocked synchronous completion polling. Its recorded completed downloads and interrupted attempt are preserved as an excluded diagnostic run, with original samples and traceback. Before starting a new fixed six-attempt series, the observer was amended to skip these optional RPCs for this profile. Basic status polling, resource collection, the fixed deadline, and client settings were otherwise retained. Discovery RPC suppression affects observation only; it does not disable peer discovery. The follow-up study record records this amendment in advance. The audit rejects optional RPC errors in any performance cohort. The main experiment had zero such errors and is unchanged.

Follow-up findings: six more verified downloads, reported separately. This series ran from 22:18:30 to 22:36:26 UTC on 2026-11-03. Deluge completed 6/6, with 17.31 MiB/s median, 15.60–19.40 MiB/s IQR, and 11.28–20.78 MiB/s range. Median completion time was 161.99 seconds. Median CPU cost was 70.39 core-seconds; median sampled anonymous/RSS peaks were 155.56 / 1,493.55 MiB. These are loaded measurements across six full transfers, alongside the original native-profile results rather than replacing them.

The later interface profile completed more consistently in this window, but the changed binding, later swarm conditions, and observer amendment prevent attributing the difference solely to IPv6. The untimed preflight proves socket availability, not which address family supplied the payload. Docker renamed the outgoing interface between fresh starts (eth0/eth1); the archived init script detects the default route each time, and every effective setting records that selected interface. The interface observation explains why the preflight's literal interface name is not held fixed.

Concurrency was variable. The 64-torrent rates ranged from 99.6–247.4 MiB/s for qBittorrent, 39.4–64.8 for Deluge, 19.8–72.9 for Transmission, 37.0–395.2 for rTorrent, 273.1–515.6 for rqbit, and 70.7–214.9 for aria2. rTorrent's upload took 84.93–88.18 seconds, with first verified payload at 60.43–61.22 seconds. Once transferring, its median 10–90% rate was 337.5 MiB/s. Its poor overall upload rate here is largely a startup effect; the exact cause was not established. Transmission's upload similarly improved from 242.6 MiB/s overall to 367.3 MiB/s in the active window.

Among the five clients with retained capped-transfer diagnostics, active-window medians were approximately 31.8–32.1 MiB/s. rTorrent's diagnostic was suppressed because its progress counter reset. Overall rates differ mainly because a roughly 32-second transfer magnifies discovery/startup costs. The case caps the seeders' payload rate; it does not emulate WAN latency or packet loss.

Some API progress counters reset during initialization/hash checking. Their startup/active-rate diagnostics are suppressed, including rqbit's large-download diagnostics and rTorrent's large/many-file/capped diagnostics. Raw samples remain available. Completed-payload wall rates do not depend on those counters' slope.

RSS is not a minimum-RAM requirement. It includes shared and mapped file pages. Deluge's largest RSS sample occurred during rechecking; rTorrent's during the large download. Shared file pages may be charged to another cgroup after a verifier or peer reads them, so process RSS can exceed the container's charged memory cap. Summed RSS can also double count shared pages. All clients approached the roughly 1.5 GiB charged-memory cap during data-heavy phases, largely through filesystem cache. The raw records retain total, anonymous, file-cache, and Docker-style working-set counters separately. No accepted client was OOM-killed.

CPU values are median cgroup CPU consumption, not elapsed time: two busy cores for one second consume two core-seconds. Lower CPU can accompany slower transfers. Deluge's large-download CPU cost was about three times qBittorrent's. The cached rechecks measure hashing plus API/state transitions. rqbit has no force-recheck endpoint, so it forgets and re-adds existing files to invoke its initialization hash check. aria2 similarly removes and re-adds the existing file with check-integrity=true, after discarding its completion sidecar. Its median recheck took 12.34 seconds, versus 2.49–4.08 seconds for the other clients. Its default 16 MiB disk cache, prealloc allocation, disabled mmap, and 100-file open-file cache were retained. Every accepted recheck visibly entered checking. Catalog timings include the client's API and initialization behavior, not just internal insertion speed. Fifteen-second idle windows do not test memory leaks.

05

Validation and collection history

The automated audit confirms 72 downloaded workloads, 38,052 filesystem file checks, 18 observed rechecks, and 36 complete upload receivers. Selected payload totals are 126 GiB downloaded and 144 GiB uploaded. Each client's measured network RX/TX exceeds its respective complete payload. Upload leechers recorded zero uploaded payload, zero failed hash bytes, and full received payloads. The tracker excludes sibling leechers from each other's discovery even after completion. There were no accepted timeouts.

The first long run stopped when qBittorrent reported completion but immediate filesystem verification found a mismatch. After clean shutdown, all 2,048 files matched their expected hashes. This is consistent with deferred disk visibility; the exact cause was not established and no persistent corruption was observed. The harness now requires qBittorrent's seed-ready state, retries and discloses transient verification failures, and fails persistent mismatches. Recheck monitoring also now requires observing checking rather than inferring work from CPU usage. Every baseline qBittorrent case was replaced with three complete new repetitions, all of which passed verification on the first attempt. The final Deluge repetition was completed separately. Unaffected baseline cases were retained without choosing the fastest results.

aria2 contributed 30 phases and 45 GiB of payload in a separate three-repeat extension. All 12 downloads passed independent SHA-256 verification on the first attempt; all six upload receivers received the complete payload, uploaded zero bytes to sibling receivers, and reported zero failed hash bytes. An initial integration attempt stopped because the adapter expected removed after stopping an already complete seed; aria2 instead reports the terminal state complete. The adapter was corrected and all three full repetitions were restarted. No measurements from that initial attempt were included.

The baseline rotated client order; corrective passes occurred later. System drift and cache state can therefore affect close comparisons. Source runs, the original failure, a post-failure diagnostic, and an explicit selection rule are retained. This was not one uninterrupted 180-phase run. aria2 ran after a Docker Desktop restart on the following day, with matching recorded CPU/memory capacity, kernel, engine version, resource limits, and fixture manifest. Its cases were not interleaved with the original five clients, so cache state and system drift may affect close rankings. Ambiguous progress diagnostics were recalculated from the original samples; wall times and resource counters were preserved.

06

Scope and reproduction

The synthetic suite is a local TCP benchmark with generated private v1 torrents, mostly warm Linux caches, two reference peers, and fixed resource limits. It establishes observed performance for these images and workloads. It does not establish maximum throughput independent of reference CPU/storage limits, cold HDD behavior, encrypted/VPN transfers, internet peer diversity, v2 metadata, latency/loss tolerance, or long-term memory use. Reference-peer CPU, throttling, network, and block-I/O counters are retained to inspect lab bottlenecks.

Run ./run.sh --output my-run --repeats 3, then python3 bench/summarize.py results/my-run and python3 bench/validate_results.py results/my-run. The README contains setup, isolation details, complete methodology, and commands to reconstruct the published selection from archived evidence. All 60 client/workload groups, variation, CPU, memory, and valid active-window rates are in SUMMARY.md, summary.csv, and trials.json.
